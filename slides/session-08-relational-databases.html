Quick review: the flat file 📄9 MIN

A flat file is one table, one file: every row is a full record. A Google Sheet, an Excel tab, or a CSV are all flat files.

ledger.csv, opened as plain text NetAcad example · Clara is invented so the pattern shows

      

        line 1 = header (column names)
        , = delimiter: a column ends here
        " = wraps a value that has quotes or commas inside
      

      

        
What you're looking at

        
This is a CSV (comma-separated values): a flat file saved as plain text. There are no columns in it. The app makes columns by counting commas. Joe's name has quote marks in it, so the whole name is wrapped in quotes and each inner quote is doubled: "Joe ""Goldentooth"" Smith".

Reach for a flat file when

        
The data is small, one person edits it, and it's mostly one kind of thing. Your homework analysis sheets are a perfect fit.

Data inconsistency

          
The store has 2 customers, but your pivot shows 4:

          
    
            
  • Joe "Goaldentooth" Smith, $1.25, and Joe "Goldentooth" Smith, $23.84. Joe really spent $25.09.
    •

Inconsistency = the same thing written in different ways. Every typo becomes a new "customer", and your numbers are wrong without any error.

Data redundancy

          
48 cells (16 rows × 3) to store 6 facts (2 customers × 3 details). The other 42 are copies. Now scale it: 200 customers shopping once a week for a year is 10,400 rows and 31,200 cells to store 600 facts. And every copy you paste carries your typos along with it. Redundancy = the same fact stored over and over.

      


      
      

        
TASK 3Two things get renamed

        
    
          
  • Joe lost his gold tooth in a fight. He's now Joe "Missingtooth" Smith. Update every one of his sales.
    • 
          
  • The supplier renamed a product: Bottle of whiskey is now Whiskey (1 bottle). Update every whiskey sale.
    • 
          
  • Use any tool you like. Edit → Find and replace is allowed.
    • 
        

        
Then prove it
Refresh your pivot. Is Joe one customer with 10 sales? Does =COUNTIF(C:C, "Whiskey (1 bottle)") give 5? Now read Joe's email column.

        
        
Data reliability

          
Find and replace only changes text that matches exactly, so:

          
    
            
  • The Goaldentooth row doesn't match "Goldentooth", so it's still separate from the real Joe.
    • 
            
  • COUNTIF gives 4, not 5. The "whisky" row was never renamed.
    • 
            
  • Joe's email is now joe.missingtooth@.... Find and replace changed a cell you never meant to touch, because "Goldentooth" was in it too.
    • 
          

          
You changed two facts and had to trust that you found every copy. Reliability = can you trust the data after it changes? With copies everywhere, you can't without checking every row.

The real argument for a database

        
All three problems come from one habit: writing the same fact (Joe's name, his address, a product name) on every row. Find and replace can repair some of it after you notice. A relational database prevents it: each fact is stored once, in its own table, and every sale points to it by ID. Next level, you'll see how.

      

    


    
    

      
The fix: a relational database 🔗10 MIN

      
A relational database splits the ledger into tables that each describe one kind of thing, then links them with ID numbers.


      
      

        🔑 primary key: the row's unique ID
        🔗 foreign key: a pointer to another table's ID
      


      
The same 6 purchases, stored relationally

      
👤 customers each name written once · two Joe Smiths, two IDs

      

      
🧾 sales just numbers pointing at the other tables

      


      

        
Guess first

        
Remember the second Joe Smith? Customer 1 and customer 3 have the same name. How does a sale know which Joe it belongs to?

      

      

        
        
        
      

      

        

          
Answer

          
By customer_id. The sale stores 1 or 3, never the name, so it can only point at one Joe. (The address only works if it's filled in and nobody shares a hut.) The same design handles your three tasks:

          
    
            
  • 🔤 Task 1: the clerk picks customer 1 instead of typing a name, so there is nothing to misspell.
    • 
            
  • 📇 Task 2: address, phone and email live once in customers: 6 cells, not 48.
    • 
            
  • ✏️ Task 3: rename Joe or the whiskey in one cell. No copies, so none can be missed, and no other cell gets touched by accident.
    • 
          

        

      


      

        
🚩 The trade-off nobody mentions

        
The sales table on its own is unreadable: "customer 1 bought product 2". To get names back you have to join the tables. You'll try it in the hands-on. Relational buys you correctness and pays for it with an extra step every time you read.

      

    


    
    

      
SQL and the client app 🖥️8 MIN

      
The database lives somewhere you can't click on. You talk to it by typing SQL (Structured Query Language) into a client app.


      

        
YOUAsk a question"What did Joe buy?"

        
→

        
CLIENT APPType it as SQLMySQL Workbench, SQLite Online

        
→

        
DATABASE ENGINEFinds and joins rowsMySQL, SQLite, PostgreSQL

        
→

        
RESULTA table comes backready for Sheets or Tableau

      


      
Read SQL like a sentence

      
SELECT name, address      -- which columns do you want?
FROM   customers          -- from which table?
WHERE  customer_id = 1;   -- only the rows that match this

      

        
Same idea as your filter view

        
SELECT is "which columns to show", WHERE is the filter dropdown. You already know the logic. SQL just writes it down so it can be rerun, shared, and checked.

      


      

        
Guess first

        
"MySQL" is the window you type into. True or false?

      

      

        
        
      

      

        

          
MySQLa database engine (server)
            
  • Stores the tables and runs the SQL
  • You talk to it through a client, such as MySQL Workbench
  • Needs installing or a hosted server

          
SQLitea database engine (just a file)
            
  • The whole database is one file, no server
  • SQLite Online is a client that runs it in your browser
  • What you'll use today: nothing to install

        

        

          
Answer: false

          
MySQL is the engine that stores and searches. The window is the client (Workbench). People mix them up because they're always used together, like saying "Gmail" for both the inbox page and the mail server.

        

      


      

        
🚩 "SQL is SQL" is only mostly true

        
The basics (SELECT, FROM, WHERE, JOIN) work almost everywhere. Small details differ between engines. Example: MySQL uses AUTO_INCREMENT for automatic IDs, SQLite doesn't. If a query from the internet errors, check which engine it was written for.

M2Look at the sales table

        
SELECT * FROM sales;

        
        
Expect
16 rows, and no names or products in them, only ID numbers. That's the "unreadable on its own" trade-off from Level 3.

      


      

        
M3JOIN it back into a readable ledger

        
SELECT s.sale_date, c.name, p.product_name, s.cost
FROM sales s
JOIN customers c ON s.customer_id = c.customer_id
JOIN products  p ON s.product_id  = p.product_id
ORDER BY s.sale_date;

        
        
Expect
Your Level 2 sheet is back: 16 sales, built on the fly, with no typos. Every sale points to customer 1 or 2, so there's nothing to misspell. JOIN ... ON means "match the ID here to the ID there". The letters s, c, p are nicknames so you don't retype table names.

      


      

        
3 more words for the next missions

        
COUNT(*) how many rows · DISTINCT each value once · SUM(cost) add up a column. WHERE keeps only the rows that match.

      


      

        
M4How many sales?

        
SELECT COUNT(*) FROM sales;

        
        
Expect
16. Same as the rows in your Level 2 sheet.

      


      

        
M5Which customers have bought something?

        
SELECT DISTINCT customer_id FROM sales;

        
        
Expect
Only 1 and 2. DISTINCT shows each value once, so 16 rows shrink to 2 buyers. Customer 3, the new Joe Smith, hasn't bought anything yet. Your Task 1 pivot showed 4 "customers". Here typos can't create extra ones, because a sale stores a number, not a typed name.

      


      

        
M6How much did Joe spend?

        
SELECT SUM(cost) FROM sales WHERE customer_id = 1;

        
Then change the 1 to a 2 for Clara.

        
        
Expect
Joe: 25.09. Clara: 5.0. In Task 1 the pivot split Joe into $23.84 and $1.25 because of "Goaldentooth". Here it's one number on the first try.

      


      

        
M7Joe loses his tooth

        
UPDATE customers
SET    name = 'Joe "Missingtooth" Smith'
WHERE  customer_id = 1;

        
Then run M3 again, and check his email: SELECT * FROM customers;

        
        
Expect
All 10 of Joe's sales in the ledger say "Missingtooth", and his email still says joe.goldentooth@.... You changed one row. In Task 3, Find and replace missed a row and changed his email.

      


      

        
M8The supplier renames whiskey

        
UPDATE products
SET    product_name = 'Whiskey (1 bottle)'
WHERE  product_id = 2;

        
Then count the whiskey sales: SELECT COUNT(*) FROM sales WHERE product_id = 2;

        
        
Expect
5, including the sale the clerk spelled "whisky" in Task 1. In Task 3, COUNTIF found only 4. Here nobody typed the product name on a sale, so there's nothing to miss. Run M3 to see the new name on every whiskey sale.

      


      

        
M9Try to sneak in a duplicate product

        
INSERT INTO products (product_name) VALUES ('Whiskey (1 bottle)');

        
        
Expect
An error: UNIQUE constraint failed. The database refuses a second "Whiskey (1 bottle)". A sheet would have quietly accepted it.

      


      

        
🚩 Honest limit

        
UNIQUE stops an exact duplicate. It won't stop someone adding "Whisky (1 bottle)" as a brand-new product. A database enforces the rules you give it. Deciding the rules is still your job.

      

      

        
Ran M1 twice by accident?

        
You'll get an error, because the tables already exist. Run DROP TABLE customers; DROP TABLE products; DROP TABLE sales; and start again from M1.
